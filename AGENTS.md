# AGENTS.md

This file provides guidance to AI coding agents working in this repository.

## Project Overview

shinywidgets is a Python package that renders [ipywidgets](https://ipywidgets.readthedocs.io) inside [Shiny for Python](https://shiny.posit.co/py/) applications. It bridges the Jupyter widget ecosystem with Shiny's reactive framework.

## Development Setup

```sh
uv sync --all-groups
uv run pre-commit install
uv run playwright install chromium
cd js && yarn install && yarn watch
```

## Common Commands

- **Type checking**: `make pyright` (or `make check-types`)
- **Linting/formatting check**: `make check-format`
- **Auto-format**: `make format`
- **Full quality check**: `make check` (format + types + unit tests)
- **Unit tests**: `make test` (or `make test-unit`)
- **Run a single test**: `uv run pytest tests/unit/test_foo.py::test_name`
- **Playwright (browser) tests**: `make test-playwright`
- **All tests**: `make test-all-local`
- **Coverage**: `make coverage`
- **Build package**: `make dist`
- **Build JS**: `cd js && yarn build`
- **Watch JS**: `cd js && yarn watch`
- **Build the website**: `make docs` (quartodoc + Quarto into `website/_site`; fails on unresolved links; log in `website/_render.log`). Needs `uv sync --group docs` once.
- **Preview the website**: `make docs-preview` (serves `website/_site` at http://localhost:8780/)
- **Check the website**: `make docs-check` (browser checks against the built site, served under `/py-shinywidgets/`)

## Website

The docs site is a Quarto project in `website/`: widget guides in `website/widgets/<slug>/index.md`, articles in `website/guide/<slug>/index.md`, gallery apps in `website/gallery/`, the API reference generated by quartodoc through `website/_renderer.py`, and the landing page in `website/index.qmd` + `website/assets/landing/`. Each page keeps its runnable `examples/` and `img/` beside it.

- `website/_tools/check_docs.py` checks that code snippets match their example files and that links resolve; it must report nothing.
- `website/_tools/sync_landing_counts.py` rewrites the landing page's category-card counts from the Widgets sidebar groups in `_quarto.yml`; `make docs` runs it before rendering, so adding a guide to the sidebar updates the landing page automatically.
- Example code blocks name their file: ` ```{.python file="examples/x.py" files="helper.py" collapse="true"} ` (`files` = extra files the app needs, `collapse` defaults to expanded). `website/_filters/example-header/` renders the header bar (open / copy / Shinylive) and turns prose links to example `.py` files into Shinylive links. Shinylive installs the page's `extra` front matter; set `shinylive-requirements: [...]` on pages without one.
- Landing images are generated from the pages' own screenshots by `website/_tools/make_landing_images.py`; re-run it after re-shooting a screenshot it uses.
- vitessce's guide is `draft: true` until `render_vitessce` ships. To publish it, remove `draft`, add it to the Scientific sidebar group and the quartodoc sections in `website/_quarto.yml`, and bump the sidebar-link count in `website/_tools/check_site.py`.

## Architecture

### Communication Layer

The core challenge is establishing bidirectional communication between Python ipywidgets and the browser, mimicking how Jupyter kernels work but using Shiny's session/message infrastructure.

**Python side (`_comm.py`, `_shinywidgets.py`):**
- `ShinyComm` replaces `ipykernel.comm.Comm` - sends widget state via Shiny custom messages (`shinywidgets_comm_open`, `shinywidgets_comm_msg`, `shinywidgets_comm_close`)
- `init_shiny_widget()` hooks into `Widget.on_widget_constructed` to intercept all widget creation and establish comms
- Widget state is serialized with buffer handling for binary data (base64 encoded since Shiny doesn't support binary messages)
- `SharedShinyComm` fans one process-global widget's messages out to a `ShinyComm` per session; shared widgets are never closed
- Global state maps in `_shinywidgets.py`: `SESSIONS`, `COMM_MANAGERS`, `SESSION_WIDGET_ID_MAP`, `WIDGET_INSTANCE_MAP`, `SHARED_WIDGETS` (widgets built in `shared_lifetime()`)
- A model the browser creates (`open_client_comm()`, e.g. pythreejs light targets, bqplot's toolbar PanZoom) is session-owned until a browser message names it; `claim_browser_created()` then makes it a `KEPT_WIDGETS` entry, so `close_render_widgets()` closes it once nothing live in the session references it. There is one sweep: give a new kind of widget an entry in it rather than a second collector
- `is_process_global()` decides which widgets every session may display (and no render or session may close); `open_shared_in()` opens one in a session. A session gets one by reference: at render time (`open_process_global_widgets()`), when a referencing widget's comm opens, and when an update names it (`open_shared_references()`). Only widgets a frontend finds without a reference (`EAGERLY_SHARED_PACKAGES`, `_REGISTRY_SOURCES`) are opened at session start (`init_session()`), so a session is never sent a shared widget it doesn't show

**JavaScript side (`js/src/output.ts`, `js/src/comm.ts`):**
- `OutputManager` extends `@jupyter-widgets/html-manager`'s `HTMLManager` to render widgets
- Custom `ShinyComm` implements the comm protocol using `Shiny.addCustomMessageHandler`
- Custom module loader (`shinyRequireLoader`) handles widget JS dependencies via require.js

### Rendering Pipeline

1. User decorates function with `@render_widget` (or specialized variants like `@render_plotly`)
2. `render_widget_base._render()` calls user function, converts result via `as_widget()`
3. Widget initialization triggers `init_shiny_widget()` which sets up the comm
4. Render returns `{model_id, fill}` to client
5. Client's `IPyWidgetOutput.renderValue()` retrieves model from manager and displays view

### Widget Coercion (`_as_widget.py`)

Not all visualization objects are ipywidgets. `as_widget()` converts:
- **altair**: Chart -> `altair.JupyterChart`
- **bokeh**: Figure -> `jupyter_bokeh.BokehModel`
- **plotly**: `go.Figure` -> `go.FigureWidget`
- **pydeck**: Deck -> `DeckGLWidget` (via `.show()`), pydeck <= 0.8 only. pydeck >= 0.9 has no widget, so `as_widget_pydeck` raises a `TypeError` pointing to `render_maplibre` + `pdk.Layer`, and `init_shiny_widget` ignores the `DeckGLWidget`s pydeck still constructs. `render_pydeck` is deprecated.

### Dependencies (`_dependencies.py`)

Handles dynamic loading of 3rd party widget JavaScript:
- `require_dependencies()` locates widget's nbextension files and creates HTMLDependencies
- Configures require.js paths so widgets can load their JS modules
- Falls back to a CDN (jsdelivr by default; `SHINYWIDGETS_CDN` overrides it) if the local extension isn't found

### Layout Integration

`set_layout_defaults()` in `_render_widget_base.py` applies smart defaults for filling layouts:
- Detects user-specified heights to avoid overriding
- Handles package-specific layout APIs (plotly margins, altair container sizing)
- Works with Shiny's fill layout system

### Adding a new renderer

When adding a `@render_*` decorator for a third-party widget package, add a matching extra to `[project.optional-dependencies]` in `pyproject.toml` (e.g., `plotly = ["plotly>=5.0.0"]`) containing everything the renderer needs, and:
- Add a row to the README's extras table
- Point the decorator's docstring and install-error messages at `pip install 'shinywidgets[<extra>]'`
- Keep example-specific data packages in the example's own `requirements.txt` (which should use `shinywidgets[<extra>]`, not the raw widget package)
- Accessor reads (`_read_accessor()`) don't depend on the render, so a re-render that reports an unchanged value doesn't re-run readers. An accessor method that computes its result from the widget itself (e.g. `visible_data()`, `camera()`) must read `self.widget`, not `self._widget`, so its readers follow a re-render

## Key Files

- `shinywidgets/_shinywidgets.py` - Widget initialization, session management, `reactive_read()`
- `shinywidgets/_render_widget_base.py` - `@render_widget` base class
- `shinywidgets/_render_widget.py` - Thin renderer subclasses (`render_plotly`, `render_altair`, etc.)
- `shinywidgets/_comm.py` - Shiny-based comm implementation
- `shinywidgets/_as_widget.py` - Widget coercion functions
- `shinywidgets/_dependencies.py` - JS dependency management
- `js/src/output.ts` - Browser-side output binding and message handlers
- `js/src/comm.ts` - Browser-side comm protocol over Shiny message handlers

## Testing

- **Unit tests** (`tests/unit/`): Cover comm transport, serialization, rendering lifecycle, widget coercion, dependencies, reactivity, and layout defaults. Run with `make test-unit`.
- **Playwright tests** (`tests/playwright/`): Browser-based integration tests that spin up real Shiny apps from `tests/apps/` fixtures. Run with `make test-playwright`.
- Pyright type checking excludes `tests/playwright/` (see `pyproject.toml` `[tool.pyright]` config).
- CI runs format, types, and unit tests across Python 3.10-3.14; Playwright tests on 3.12 only.
